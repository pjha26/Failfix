# FailFix audit and fixes — 28 October 2026

What this repo does: FailFix reviews failing TypeScript/Vitest tests and deployment logs, links findings to supplied evidence, and exports proposed patches for local review. Public GitHub import reads limited configuration and run metadata. This audit assumes the documented single Node.js process and replica; the app does not execute submitted code or deploy changes.

## Fixed findings

1. **Log trimming changed evidence locations and weakened the byte limit.**
   - **What this is:** [The deployment input contract](../lib/deployment-contracts.ts) validates logs before [signature checks](../lib/deployment-analysis.ts) generate line references.
   - **Problem:** Two blank lines before an error were removed, so line 3 was reported as line 1. A log larger than 32 KiB could also pass if the extra bytes were leading/trailing whitespace.
   - **Fix:** Preserve the submitted text, check nonempty content without transforming it, and apply the byte bound to the original string. Regression tests reproduced both failures before the fix.
   - **If left unfixed:** Evidence links select unrelated lines and the displayed log limit does not match server validation.

2. **Windows uploads selected the wrong source or log text.**
   - **What this is:** The [test desk](../components/workspace.tsx) and [deployment desk](../components/deployment-workspace.tsx) select text when an evidence link is clicked.
   - **Problem:** Uploaded CRLF files retain two-character line endings in state, while browser textareas expose one-character newlines. Offsets counted from the original content skipped characters and included part of the next line.
   - **Fix:** Compute source selection offsets from LF-normalized text and deployment offsets from the textarea's actual value. Original input bytes remain available for patch generation. Desktop and mobile regressions reproduced the incorrect selections before the fix.
   - **If left unfixed:** A correct line reference can still highlight the wrong text, especially for files uploaded from Windows.

3. **Similar script names could receive an unrelated patch.**
   - **What this is:** The [missing-build signature](../lib/deployment-analysis.ts) can offer a narrow `package.json` patch for a Next.js project without a `build` script.
   - **Problem:** `Missing script: "build:prod"` and `Missing script: "build-test"` matched the plain `build` signature. The proposal added `build`, leaving the actual missing command unresolved.
   - **Fix:** Match the complete quoted or unquoted script identifier. Tests cover similarly named scripts while existing tests retain the valid missing-build flow.
   - **If left unfixed:** The user can download a plausible configuration change that does not address the supplied error.

4. **One malformed config file aborted the whole public import.**
   - **What this is:** [Public GitHub import](../lib/github-public.ts) decodes supported small files as strict UTF-8 text.
   - **Problem:** An invalid-UTF-8 `.nvmrc` raised a decoding exception after a valid `package.json` had already been read. The entire import failed instead of retaining the useful configuration.
   - **Fix:** Catch decoding/content-validation failures for that file, add a warning, and continue. Tests cover invalid UTF-8 and null-containing binary content; network and GitHub API failures still follow their existing error paths.
   - **If left unfixed:** A repository's unrelated malformed file prevents investigation of otherwise valid configuration.

## Dependency and verification results

- `npm audit --json` reported zero known vulnerabilities: zero critical, high, moderate, low, or informational findings. No package or lockfile changes were needed.
- 107 unit/API/SDK checks passed. The new backend regressions produced five failing cases before their fixes.
- 48 production-browser checks passed across desktop and 390px mobile, including actual selected-text assertions for CRLF uploads. The new/strengthened CRLF checks failed in both viewports before their fixes.
- Typecheck, lint, and production build passed. Documentation links and architecture diagrams were validated.
- No live model calls or paid service requests were needed for this audit. Provider behavior is covered with HTTP mocks; previous live smoke checks remain recorded separately in [evaluation status](../evals/results.md).

## Scope and remaining limits

Read the request-body/origin checks, request/result contracts, patch construction, manual-review path, provider/error handling, admission limits, public-import path, build signatures, API handlers, CI configuration, and the affected client evidence flows and tests. This was not a line-by-line review of all presentation markup or CSS.

Not checked: deployed-host/proxy configuration, penetration testing, physical-device GPU performance, concurrent production load, or broad live-model accuracy. In-memory admission limits remain suitable only for the documented single-process deployment; multi-replica scaling and account-connected repository writes require separate work. Literal regression-import checks are not a code sandbox, and the app does not claim they prove generated code safe to execute.

Verdict: the confirmed functional bugs are fixed and the current dependency audit is clean. These results are not a general security certification.
